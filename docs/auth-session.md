# 登录态保持

## 行为

登录令牌与绑定的用户资料保存在**当前站点的 `localStorage`**。刷新页面、
关闭后重新打开同一站点时，前端调用 `/auth/me` 验证并恢复登录态。

令牌失效时的处理分两种情况，这个区分很重要：

| 情况                  | 行为                                                       |
| --------------------- | ---------------------------------------------------------- |
| 网络错误 / 服务端 5xx | **保留**登录态，仅在本地资料未过期且与当前令牌绑定时才恢复 |
| 业务接口返回 401      | 清除本地登录态并跳转登录页                                 |

也就是说：**后端挂了不会把用户登出**，只有明确的鉴权失败才会。这条规则的用意是避免
服务端抖动一次就把用户踢出去，同时保证真正失效的令牌不会继续留在本地。

还有一条容易被忽略的并发保护：401 清除登录态之前，会先确认这个 401 属于**当前**令牌 ——
否则「旧请求延迟返回的 401」会把用户刚登录成功的新令牌一并清掉。
`checks/auth-session-regression.mjs` 专门覆盖了这个竞态。

## 令牌有效期

`ACCESS_TOKEN_EXPIRE_MINUTES` 默认 `10080`（7 天），在 `background/.env` 中调整，改完需重启后端。

**这是固定期限的 JWT，不是滑动续期**：已签发的令牌无法延长有效期，到期必须重新登录。
若以后要做「活跃用户自动续期」，需要额外引入 refresh token 机制。

## 容易踩的三个点

1. **浏览器存储按站点隔离**：`localhost` 与 `127.0.0.1` 不共享登录态，不同端口也不共享。
   调试时请固定用同一个地址，否则会误以为「登录丢了」。
2. **401 与 5xx 不能混为一谈**：把网络故障当鉴权失败处理，会导致服务端一抖动用户就被登出。
3. **旧请求的 401 会误伤新令牌**：见上面的竞态保护。
